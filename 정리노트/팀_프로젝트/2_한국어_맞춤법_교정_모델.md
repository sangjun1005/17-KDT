### 제외 대상 — 삭제가 아니라 표시

```
[제외 사유별 건수]

  HATE_ONLY_INPUT       3,829  (0.339%)

  LEN_GROWTH_EXTREME      101

```

`hate-speech`는 원본이 혐오 표현을 자리표시자로 치환한 것이다.
**입력 전체가 `hate-speech`인 행은 학습에 쓸 수 없다.**

```
[target에만 hate-speech가 있고 input은 일반 문장]
  'ㅡㅡ 화나요'                              → 'hate-speech'
  '우선은 좀 더 지켜보기오 했대요 근데...'     → 'hate-speech'
```

**정답이 통째로 날아간 행이 30건 있다.** 그대로 두면 모델이 "아무 문장이나 `hate-speech`로 바꿔라"를 배운다.

```
[정답이 지나치게 길어짐] 101건
  '헉'         → '헉... 2주에 한 번씩 등교하는군요.'

  '잼써요!'     → '잼써요! ㅋㅋㅋ'

[비식별화 토큰 변경] 40건
  '저는 name5 name6 해쭈 name8 봅니더@!' → '저는 name5, name6, name7, name8 봅니다! @'
```

**`해쭈`가 `name7`이 됐다.** 비식별화 처리가 교정 단계에서 한 번 더 들어간 흔적이다.

> **"제외 대상 표시(삭제하지 않음)"라는 절 제목이 이 프로젝트의 태도를 보여 준다.**

## 2-5. 문서 단위 분할 — 누수를 두 겹으로 막는다

```
문서 21,335개, 문서당 발화 수 중앙값 32, 최소 26
공유 문장 142개로 연결된 문서 묶음: 112개 (묶인 문서 271개, 최대 묶음 10개 문서)
```

**그런데 한 겹 더 있다.** 서로 다른 문서에 **똑같은 문장**이 들어 있는 경우다.
(전달받은 메시지를 그대로 옮긴 경우 등) 공유 문장 142개가 문서 271개를 112개 묶음으로 연결했다.

```
flag_digit_changed   '되면 멋있을텐데 지금은 그냥 고시생1..' → '...그냥 고시생 하나...'
flag_alpha_changed   '무드등 같은가유 예브답'  → '무드등 같은 건_x0008_가요? 예쁘다.'   ← 제어문자
flag_alpha_changed   '퐁당퐁당러브랑'         → '퐁당퐁당 lovr랑'                    ← 오타
flag_alpha_changed   '신혼부부전용 주택청약 ㄱㄱ' → '신혼부부 전용 주택 청약. Rr'       ← ㄱㄱ→Rr
flag_alpha_changed   '+%EB%B7%94...'         → 'ERROR:#REF!'                      ← 엑셀 오류
flag_emoji_changed   '항상 큰맘 먹고 시작해요.)' → '항상 큰맘 먹고 시작해요. :)'
flag_partial_...     '안뇽' → '안뇽?'  (×2)   '시상에' → '시상에.'
```

**`ERROR:#REF!`와 `_x0008_`은 정답 파일이 엑셀을 거치며 깨진 흔적이다.**

```
train: 986,728 → 986,718 (제거 10행)
validation / test: 변경 없음
```

> **validation·test는 손대지 않았다.** v3b 대비 **파일 해시가 동일**함을 확인했다.
> 평가 데이터는 건드리지 않는다는 원칙을 해시로 증명한 것이다.

## 2-8. 지표를 먼저 정한다 — Balanced EM

**Exact Match만 쓰면 안 되는 이유가 이 데이터에 있다.**

```
전체의 13.9%는 unchanged — 고칠 게 없는 문장
```

**입력을 그대로 복사하는 모델**을 만들면 그 13.9%를 전부 맞힌다.
아무것도 안 배웠는데 EM 0.135가 나온다.

```
Balanced EM = (교정 필요 행 EM + 원문 유지 행 EM) / 2
```

<table fit-page-width="true" header-row="true">
<tr><td></td><td>exact_match</td><td>교정 필요 EM</td><td>원문 유지 EM</td><td><strong>Balanced EM</strong></td></tr>
<tr><td>입력 복사 (기준선)</td><td>0.1351</td><td>0.0000</td><td>1.0000</td><td><strong>0.5000</strong></td></tr>
<tr><td>pko-T5 (NFKC)</td><td>0.6965</td><td>0.6693</td><td>0.8707</td><td><strong>0.7700</strong></td></tr>
</table>

**입력 복사는 정확히 0.5가 된다.** 교정 필요 행을 하나도 못 맞히고(0.0),
원문 유지 행은 전부 맞히니(1.0) 평균이 0.5다.

**0.5가 바닥선인 지표를 만든 것이 핵심이다.**
17-2조가 "전부 호중구로 찍기 = 0.5932"를 기준선으로 삼은 것과 같은 발상이다.

### 함께 보는 지표들

<table fit-page-width="true" header-row="true">
<tr><td>지표</td><td>무엇을 재나</td><td>주의</td></tr>
<tr><td>Balanced EM</td><td>교정/유지 양쪽</td><td><strong>주지표</strong>. 0.5가 바닥</td></tr>
<tr><td>CER</td><td>문자 오류율</td><td>낮을수록 좋다</td></tr>
<tr><td>chrF</td><td>문자 n-gram F</td><td>직접 구현 — sacrebleu와 미대조</td></tr>
<tr><td>ROUGE-2 (어절)</td><td>어휘 겹침</td><td><strong>한 글자 차이에도 급락.</strong> 단독 사용 금지</td></tr>
<tr><td>over_correction_rate</td><td>고칠 것 없는데 고침</td><td></td></tr>

</table>

**과교정률과 교정누락률을 나눠 보는 것**이 이 과제의 핵심이다.
둘은 **반대 방향의 실수**라 하나로 합치면 상쇄되어 보이지 않는다.

## 2-9. NFKC 함정 ⭐

**이 프로젝트에서 가장 값진 발견이다.**

```
             exact_match  balanced_em    cer
model|NFKC        0.6965       0.7700  0.0355
model|raw         0.5269       0.5649  0.1025
```

**같은 예측인데 EM이 17%p 차이 난다.**

```
정답 : ㅋㅋㅋㅋㅋㅋ    (U+314B 호환 자모)
예측 : ᄏᄏᄏᄏᄏᄏ     (U+110F 초성)
```

**화면에서는 거의 같아 보이지만 다른 문자열이다.**

원인은 pko-T5의 SentencePiece tokenizer가 입력을 **NFKC 정규화**하기 때문이다.
호환 자모 `ㅋ`이 초성 `ᄏ`으로 바뀌고, 그게 출력에도 그대로 나온다.

**한국어 채팅 데이터에는 `ㅋㅋ`, `ㅠㅠ`, `ㅇㅇ`이 아주 많아** 이 차이가 크게 나타난다.

### 해결 — 모델을 건드리지 않고 후처리

```python
from ko_postprocess import restore_compat_jamo
PP = [restore_compat_jamo(p) for p in PRED]
```

**홀로 쓰인 옛 한글 자모를 호환 자모로 되돌리는 결정적 규칙이다.**

<table fit-page-width="true" header-row="true">
<tr><td></td><td>exact_match</td><td>balanced_em</td><td>cer</td><td>과교정률</td></tr>
<tr><td>raw, 후처리 전</td><td>0.5269</td><td>0.5649</td><td>0.1025</td><td>0.3831</td></tr>
<tr><td><strong>raw, 후처리 후</strong></td><td><strong>0.6896</strong></td><td><strong>0.7658</strong></td><td><strong>0.0374</strong></td><td><strong>0.1299</strong></td></tr>
<tr><td>NFKC (참고)</td><td>0.6965</td><td>0.7700</td><td>0.0355</td><td>0.1293</td></tr>
</table>

```
후처리로 문자열이 바뀐 예측: 12,893행 (23.56%)
raw Balanced EM 개선: +0.2009 (CI95 0.1925 ~ 0.2091)
정답이었다가 틀리게 된 행: 3

```

**8,908 얻고 3 잃었다.** 2,969:1이다.

**모델도 데이터도 바꾸지 않았다.** 출력 문자열에 결정적 규칙 하나를 적용했을 뿐인데
Balanced EM이 0.5649 → 0.7658로 올랐다.

> **"모델 성능이 낮다"고 결론 내리기 전에 출력을 직접 눈으로 봐야 하는 이유**가 이것이다.
> 오류의 35.9%가 실력이 아니라 문자 인코딩 문제였다.

**두 개가 실패했으므로 Beam을 쓰지 않는다.** 점수 하나가 올랐다고 채택하지 않는다.

**출력이 다른 행은 2.63%뿐이다.**

```
출력이 다른 행: 1,439 / 54,730 (2.63%)
Beam3가 더 높은 행: 480 | Greedy가 더 높은 행: 363 | 같은 점수: 596
```

**실제 사례가 설득력 있다.**

```
[Beam3가 더 좋은 경우]
 입력 : 헐 죽기까지
 정답 : 헐, 죽기까지.
 Greedy: 헐, 죽기까지      ← 마침표 누락
 Beam3 : 헐, 죽기까지.     ← 맞음

[둘 다 틀린 경우]
 입력 : 어떤 사람 3개월 하루빼고 매일 한 인증글 올라와신디 된댘ㅋㅋㅋ
 정답 : ... 올라왔는데 된대. ㅋㅋㅋ
 Greedy: ... 올라와 있던데 된대. ᄏᄏᄏ
 Beam3 : ... 올라와서 된대. ᄏᄏᄏ
```

**`올라와신디`가 무슨 말인지 모델이 모른다.** 둘 다 그럴듯하게 지어냈다.
그리고 `ㅋㅋㅋ` → `ᄏᄏᄏ` 문제도 여기 보인다.

> **샘플링(Top-k/Top-p/Temperature)은 쓰지 않았다.**
> "교정은 정답이 사실상 하나인 과제이고, 실행마다 결과가 달라져 재현·평가가 어렵다"는 이유다.
> **다만 이 판단은 이론적 근거이며 실험으로 검증하지 않았다**고 명시했다.
> 파이토치 NLP 4장에서 GPT-2 생성에 샘플링을 쓴 것과 대비된다 — **과제의 성격이 다르다.**

## 이 장 정리

### 한 줄 요약

**모델을 고르는 일보다 "무엇을 정답으로 볼 것인가"를 정하는 일이 훨씬 컸다.**
노트북 15개 중 5개가 전처리, 3개가 정답 품질과 오류 분석이다.

### 이 프로젝트의 절차 (그대로 따라 할 만하다)

```
1. 원본 해시를 찍고 시작한다
2. 스트리밍으로 파싱한다 (json.load 금지)
3. 제외 대상을 지우지 말고 사유를 표시한다
4. 문서 단위 + 공유 문장 묶음 단위로 분할한다
5. 분할 후 분포가 같은지 확인한다
6. 품질 플래그를 붙이고 표본을 사람이 판정한다
7. 판정된 것만 제거하고 동결(SHA256)한다
8. 별도 노트북에서 앞 단계를 재검증한다
9. 선택 규칙을 결과보다 먼저 등록한다
10. 모델을 비교하고 문서 단위 bootstrap으로 CI를 본다
11. 오류를 유형별로 분류해 모델 탓/데이터 탓을 가른다
12. 설정을 해시로 잠근다
13. Test를 딱 한 번 연다
```

### 자주 틀리는 것

- 큰 JSON을 `json.load`로 연다 → 메모리 폭발
- **문장부호·인코딩 차이를 모델 성능 문제로 본다** → 오류의 36%가 NFKC 문제였다
- Exact Match만 본다 → 입력 복사 모델이 유리해진다
- **행 단위로 bootstrap한다** → 같은 대화의 발화는 독립이 아니다
- 문서 단위로 나눴으니 누수가 없다고 믿는다 → 입력 텍스트 중복 17%
- 품질 플래그를 그대로 삭제한다 → 멀쩡한 11만 행이 날아갈 뻔했다
- 결과를 보고 선택 기준을 정한다 → 무엇이든 정당화된다
- Validation 수치를 Test인 것처럼 쓴다
