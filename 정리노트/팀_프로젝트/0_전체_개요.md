# 팀 프로젝트 — 전체 개요

`17-KDT`의 팀 프로젝트 폴더 두 개를 정리한 것이다.
수업 챕터가 아니라 **하나의 문제를 팀이 끝까지 끌고 간 기록**이라 정리 방식도 다르다.

| 장 | 폴더 | 주제 | 노트북 |
| --- | --- | --- | --- |
| 1 | `17-team4` | 천안시 의료취약지역 지도 | 12개 (`Project/notebooks/`) |
| 2 | `pro4_team3_최종` | 한국어 맞춤법 교정 모델 | 15개 |

`17-2조`(백혈구 4종 분류)도 팀 프로젝트지만 **딥러닝 정리의 프로젝트 챕터**에 이미 있어
거기에 실측치를 보강했다. 새 페이지를 만들지 않았다.

## 두 프로젝트의 성격이 정반대다

| | 1장 · 천안시 지도 | 2장 · 맞춤법 교정 |
| --- | --- | --- |
| 다루는 것 | **표 데이터** (인구·의료기관·독거노인) | **텍스트 생성** (seq2seq) |
| 규모 | 34개 읍면동 | 발화 **1,129,363건** |
| 핵심 기술 | 판다스 병합·가중치 설계 | pko-T5 미세조정·디코딩 |
| 어려웠던 지점 | **키가 안 맞는 병합** | **정답 라벨 자체의 품질** |
| 결과물 | 웹 대시보드 + FastAPI | 잠긴 설정 + Validation 지표 |
| 수업 연결 | 판다스·시각화 3·6·7장 | 파이토치 NLP 4장, 딥러닝 10장 |
| 완성도 | 분석 완료, 점수 산출까지 | Validation까지. **Test 미실행** |

## 두 프로젝트가 공통으로 보여 주는 것

**데이터 합치기가 모델링보다 오래 걸린다.**

1장은 노트북 12개 중 **9개가 전처리와 병합**이다. 모델은 아예 안 쓴다.
2장은 15개 중 **5개가 전처리와 검증**이고, 그중 하나는 오직 "앞 단계를 믿을 수 있는지"만 확인한다.

**그리고 둘 다 "합치는 키"에서 한 번씩 크게 막혔다.**

```
1장: 병원 데이터는 법정동(쌍용동), 인구 데이터는 행정동(쌍용1·2·3동)
     → 31개 중 15개만 매칭. 노트북에 "# merge fail" 이 그대로 남아 있다

2장: 같은 입력에 서로 다른 정답이 붙은 행이 train에 116,635건(11.8%)
     → 모델이 무엇을 배워야 할지 데이터가 알려 주지 않는다
```

**해결 방식도 비슷하다 — 데이터를 바꾸지 않고 출처를 바꾸거나, 문제를 표시만 하고 남겼다.**

## 1장에서 배울 것

- 공공데이터의 **행정동 ↔ 법정동** 문제와 그 해결
- 사분위수·중앙값으로 **기준선을 데이터에서 뽑아내기**
- 네 가지 가중치(동일·목적기반·CRITIC·퍼지 AHP)로 **같은 데이터에서 다른 순위 만들기**
- 분석 결과를 FastAPI로 서비스하기 (웹 백엔드 5장의 `17-aws-docker`가 바로 이 프로젝트다)

## 2장에서 배울 것

- **517MB JSON을 스트리밍으로 읽기** (`json.load` 금지)
- 문서 단위 분할과 **누수 점검** (공유 문장으로 연결된 문서 묶음까지)
- **지표를 먼저 정하고 결과를 보는** 절차 — 사전 등록된 선택 규칙
- **Balanced EM** — 입력을 그대로 복사하면 0.5가 되는 지표를 만든 이유
- `SHA256` 잠금으로 **"결과를 보고 설정을 바꾸지 못하게" 강제하기**
- Greedy vs Beam Search를 **규칙으로 판정**하기
